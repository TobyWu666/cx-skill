# 驗收清單

Codex 負責寫程式，你負責判斷。驗收是派工值不值得的關鍵，也是最容易在趕時間時偷工的一步。
原則只有一句：**拿事實對照，不拿它的自述對照。而且要記得，AI 寫的程式碼會以測試抓不到的方式出錯。**

## 1. 先看結果檔

```bash
jq '{status, thread_id, touched_files, new_commits, errors}' <out>/result.json
cat <out>/final.md
```

- `status` 不是 `completed` 的話，先看 SKILL.md 的「狀況處理」。
- `new_commits` 不是空的：Codex 違反 brief 自己 commit 了。內容可能沒問題，但要告訴使用者，之後要不要保留這個 commit 由使用者決定。
- `pre_existing_changes > 0`：派工前就有未提交的改動，看 diff 時要分清楚哪些是 Codex 改的。

## 2. 先檢查測試有沒有被改弱，再相信測試結果

diff 有動到現有測試的話，**先看這些改動**：

- 刪除測試、加上 skip 或 xfail、把測試註解掉：都當作那個測試其實沒過。
- 放寬斷言，例如精確比對改成 contains 或 truthy、擴大錯誤型別、放寬容許誤差：處理方式相同。
- brief 沒有要求修改的現有測試：這是改了驗收標準，不是修 bug 的一部分。要退回，或至少回報。

## 3. 自己重跑驗證

在 repo 裡實際跑一次 brief 裡的 test、lint、build 指令，讀輸出。測試通過是**必要條件，不是充分條件**。

依改動類型多做一些檢查：

- **刪除或改名**：在整個 repo 用 grep 搜舊名字，確認沒有殘留的引用。
- **資料庫 schema 或 migration**：套用、回滾、再套用一次。
- **有狀態的功能或 UI**：實際操作一次，不要只確認能編譯。可以用 run skill 或模擬器。

## 4. 拿 diff 對照 brief

```bash
git -C <repo> status --short
git -C <repo> diff
git -C <repo> diff --cached     # Codex 有時會自己 stage
```

`??` 的新檔案不會出現在 diff 裡，要逐一打開來看。

- **超出範圍**：沒被要求的重構、改名、重新排版，還有那種「順便改一下」。這是委派工作最常見的品質問題。
- **漏做**：邊界情況、清理工作、brief 裡列的每一點是不是都做到了。
- **默默做的設計決定**：看起來合理也不要直接接受。先弄懂它為什麼這樣做，再決定要不要保留，而且要寫進回報。

## 5. AI 程式碼常見問題掃描

以下這些問題，測試全綠也照樣可能存在：

- **寫死的成功值或假資料**：本來應該做真正工作的路徑，卻直接回傳固定值，例如 `return .success`、`{status: "ok"}`。
- **吞掉錯誤**：catch-all 之後回傳預設值，原本應該往外拋的錯誤被藏起來了。
- **不存在的 API**：新用到的套件、方法、參數，要對照 lockfile 或實際安裝的版本，確認真的存在。
- **沒用到的東西**：沒用的 import、沒人呼叫的 helper、`// Step 1` 這種鷹架註解、只是在覆述程式碼的註解。
- **重複造輪子**：檔案裡已經有現成的寫法（HTTP client、錯誤處理、logging），它卻又寫了一套。
- **過度設計**：沒有人呼叫的選用參數、設定開關、抽象層。
- **不可能發生的防禦**：型別或契約已經保證不會發生的情況，還加 null 或型別檢查。
- **只測內部實作的測試**：mock 專案自己的函式、斷言某個內部 helper 被呼叫。這種測試會通過，但很脆弱，也沒有實際價值。

## 6. 判定

| 結果 | 動作 |
| --- | --- |
| 全部通過 | 使用者授權過就 commit（一個任務一個 commit），沒授權就留在 working tree 給使用者看 |
| 小問題，例如一個沒用的 import | 你可以直接修，但要在回報裡說明 |
| 實質問題 | 寫增量 brief，用 `--session <thread_id>` 返工，然後重新完整驗收 |
| 方向錯了，或前提錯了 | 停下來，先跟使用者確認。是否丟棄改動要先看過再決定 |
| 返工兩輪還不行 | 停下來，向使用者說明狀況和你的建議 |

## 7. 回報給使用者：如實呈報，不要自己吞下來

- Codex 做的設計決定，以及合理但 brief 沒要求的改動，都要列出來。
- 你決定不擋的小瑕疵也要列出來，讓使用者可以推翻你的判斷。
- 要完成任務就必須超出範圍的時候，先問使用者。擴大範圍是使用者的決定，不是你的，也不是 Codex 的。
